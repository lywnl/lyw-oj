## 失败路径与真实验证

实际 cgroup 记录为 CPU `100000 100000`、PIDs `128`、内存 `99999744`、额外 swap `0`；Docker 请求中的 memory/memorySwap 均为 `100000000`，内核页大小 `4096`。两类持续创建线程程序均观测到 `current=128` 和 `events=max 4`，确认实际拒绝事件。正常 A+B 在相同默认限额下通过。

执行等待超时与已退出后的题目超时分开验证；旧容器移除确认与任务 Future 顺序由生命周期测试核对，真实超时测试再次核对旧 ID 消失与后续恢复。真实 TCP 端点测试确认控制请求等待、Netty upgrade/stats 启动有界、客户端 EOF 和相关线程最终退出。

删除失败使用真实容器及 remove 命令故障注入，证明资源隔离、名额保留和后续拒绝。调度时序、创建结果不确定、删除确认、双核心恢复交错、目录失败、消息幂等等采用 Mockito/闩锁。没有将这些替身结论表述为真实数据库、MQ 或完整 HTTP 链路验证。

历史失败已保留在主报告：`unit-01` 的 7 个测试替身错误；`docker-smoke-01` 缺少 ARM64 Linux epoll 原生库；`docker-full-01` 的 1 个内存页对齐断言错误。均已修复并由当前有效批次覆盖。`compile-01` 仅是跳过测试的编译记录，不计入测试通过数。早期 DEBUG wire 日志未原样转存，避免保留无关容器连接信息；失败命令、原始日志哈希及原因摘要仍保留。

## 限制与交付条件

- 未加入用户/接口限流，未实现正常退出后主动遗留后台子进程的完整追踪和隔离；这属于已明确的后续范围。
- 沿用 `getMaxUsage()` 内存统计；不能据此宣称 cgroup v2 下判题内存统计准确。
- `case_judge_res` 仍是 TEXT，本轮没有验证完整数据库的大输出存储边界；`exe_message` 只做了 500 个 Unicode 字符以内的诊断摘要控制。真实存储集成测试未执行，仅同步接口并完成测试编译。
- 文件时间预算不能中断内核中不可中断的文件系统调用。超过 64 层或无法安全清理的目录会失败隔离，不自动恢复或放宽限制。
- 真实环境为 JDK 17 / Linux ARM64 / Docker Desktop cgroup v2；没有验证其他架构、生产环境、高并发或性能收益。
- 部署切换时需要核对旧容器与同名目录归属，当前代码会拒绝接管。回退应只撤回本轮登记的模块改动和新增文件；本轮没有部署，无需回滚生产数据或资源。
