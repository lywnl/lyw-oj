## Context

当前 `oj-judge` 的 `DockerSandBoxPool` 保存可用容器 ID，调用方线程通过 `getContainer()` 获取容器后直接执行 Docker 操作，再通过 `returnContainer()` 归还。同步判题来自 `oj-friend` 的 Feign 调用，异步判题由 `JudgeConsumer` 消费 RabbitMQ 消息并在判题方法返回后手动 ACK。现有实现缺少任务级队列、统一 Worker 生命周期和核心容器故障补建能力。详细行为要求见 `specs/judge/container-pool/spec.md`。

## Goals / Non-Goals

**Goals:**

- 将判题调度改为有界 `JudgeTask` 队列和容器执行 Worker，保证单任务单次消费、单容器单任务执行。
- 按核心数量、队列容量和最大数量实现类似 `ThreadPoolExecutor` 的扩容、临时资源回收和满载拒绝。
- 让核心容器从服务启动后持续可用，异常退出时恢复核心资源数量。
- 保持同步 Feign 判题和 RabbitMQ 异步判题的业务入口兼容，并使异步消息在任务完成前不被确认。
- 将用户代码清理、容器健康判断和异常隔离集中到执行生命周期中。

**Non-Goals:**

- 不改变题目、提交记录、竞赛或消息的数据模型。
- 不增加新的微服务、消息中间件或数据库。
- 不在本次改造中支持新的编程语言或改变判题比较规则。
- 不把 RabbitMQ 改造成容器池内部的唯一任务队列；RabbitMQ 仍负责跨服务投递和持久化，容器池负责本地执行调度。

## Decisions

### 使用有界任务队列替代容器 ID 队列

池维护 `BlockingQueue<JudgeTask>`，提交方只提交任务并获得同步结果 Future 或异步完成句柄。Worker 从任务队列原子取出任务，任务被取出后不再由其他 Worker 执行。一个 `ContainerWorker` 独占一个 Docker 容器，执行 Docker 操作时不持有池的全局锁。

选择该方式是因为当前“请求线程获取容器”的模型会让 Tomcat 或 RabbitMQ 消费线程承担长时间 Docker 执行；任务队列能把入口线程和容器生命周期解耦。相比继续维护容器 ID 队列，Worker 模型也能直接表达执行中、空闲、停止和失效状态。

### 采用线程池式扩容顺序

任务提交遵循以下顺序：核心 Worker 未达到核心数量时创建核心 Worker；否则尝试入队；队列已满且 Worker 未达到最大数量时创建临时 Worker；队列已满、没有空闲 Worker 且无法再创建容器时拒绝任务并返回 `SYSTEM_BUSY`。推荐初始参数为核心 4、最大 8、队列容量 16、临时 Worker 空闲存活 60 秒，且全部由现有 Nacos 配置体系管理。

选择有界队列是为了让最大 Worker 数真正限制 Docker 并发，避免无限队列掩盖扩容和拒绝规则。参数保留可配置性，不把推荐值固化为不可变常量。

### 核心资源与临时资源分离管理

服务启动时创建核心容器及其 Worker，并让核心 Worker 持续等待任务；核心资源不参与空闲回收。若启动期间任一必需核心容器创建或启动失败，Bean 初始化失败并阻止判题服务就绪。服务运行期间池需要周期性或事件驱动地检查容器状态，发现核心容器失效时隔离、销毁并补建新的核心 Worker。临时 Worker 仅在没有执行任务且空闲超过存活时间时退出，退出前必须确认没有正在执行的任务。

相比统一使用空闲超时回收，单独维护核心资源可以满足常驻要求；相比服务重启时无条件复用旧容器，启动时必须校验容器状态，避免将退出或不可执行的容器纳入可用资源。

### 同步和异步入口共享提交模型

`SandboxPoolServiceImpl` 将判题请求包装为 `JudgeTask` 并提交给池。同步调用等待 Future 获取结果；异步调用由 RabbitMQ 消费端提交任务，并在任务完成、结果写入和失败处理完成后才 ACK。当队列已满且没有空闲 Worker、也无法创建新容器时，池拒绝同步任务并返回 `SYSTEM_BUSY`；异步任务由 `JudgeConsumer` 使用 `basicNack(requeue=false)` 交给死信队列，`DeadLetterConsumer` 负责更新 Redis 失败状态。应用不在池层维护第二套 RabbitMQ 重试计数。

选择完成后 ACK 是为了避免 `oj-judge` 在本地任务尚未执行时崩溃造成消息丢失；池满拒绝使用 `basicNack(requeue=false)` 并统一交给死信消费者收敛状态，避免池、消费者和死信消费者重复维护重试计数。RabbitMQ 的预取数量需要与本地队列及 Worker 容量匹配，不能通过立即 ACK 来掩盖本地过载。

### 按故障类型决定容器是否复用

编译失败、输出不匹配、超时和资源超限属于用户代码判题结果；清理工作目录后，健康容器继续复用。Docker API 失败、容器退出或 exec 无法创建属于容器故障；当前容器标记失效并隔离，不再接收任务，随后销毁并重建，核心资源必须补齐。

这种区分可以避免为普通编译错误重复创建容器，同时避免把已经损坏的容器放回队列造成连续失败。

## Risks / Trade-offs

- [消息确认延迟] RabbitMQ 消息会在整个判题期间保持未确认，长任务可能占用消费者信道。→ 限制判题超时时间，配置合理的 prefetch，并监控未确认消息数量。
- [本地队列重启丢失] 已被 ACK 但仍在本地队列中的任务可能因进程崩溃丢失。→ 异步消息只在任务完成后 ACK；同步任务在进程退出时通过请求失败返回，不承诺跨进程恢复。
- [容器状态污染] 用户代码可能留下编译产物或改变容器运行状态。→ 每个任务结束都清理挂载目录并执行健康检查；异常容器隔离重建。
- [扩容资源成本] 临时容器会增加 Docker 内存和 CPU 使用，最大数量过大可能影响宿主机。→ 使用有界队列、最大数量配置和运行指标，先采用核心 4、最大 8 的保守默认值。
- [并发状态竞态] 扩容、缩容、故障补建和任务归还可能同时发生。→ 队列操作使用其内部并发保证；Worker 数量和生命周期使用原子计数或专用锁；Docker 执行不持有全局锁，并通过状态转换防止重复停止和重复完成。

## Migration Plan

1. 先增加池配置和任务/Worker 生命周期抽象，保留现有同步与异步入口的外部路径。
2. 将 `SandboxPoolServiceImpl` 切换为池任务提交，将 `JudgeConsumer` 调整为任务完成后确认消息。
3. 在本地使用替身 Docker 客户端验证队列调度、扩容、拒绝、缩容、容器故障和消息确认场景，再连接真实 Docker、RabbitMQ 和 Redis 做集成验证。
4. 发布时先使用原有核心数量和较小最大数量观察并发、队列积压、拒绝数和容器重建指标；出现异常时回滚应用版本并清理由新版本创建的临时容器。

## Open Questions

无。当前规格所需的队列容量、核心/最大数量、拒绝语义、ACK 时机和核心容器恢复行为已按前述方案确定；更细的监控指标名称和测试替身实现可在任务拆分阶段补充，不改变本设计。
