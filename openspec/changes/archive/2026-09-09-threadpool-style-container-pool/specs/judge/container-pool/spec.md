## Purpose

为在线判题提供受控的容器执行能力，使判题任务通过有界队列调度到独占执行资源，并在高峰、低峰和容器故障场景下保持可预测的并发与可靠性。

## ADDED Requirements

### Requirement: 判题任务必须通过有界队列调度

系统 SHALL 接受判题任务并将其放入受容量限制的任务队列，由可用执行资源消费；提交方不得直接竞争或共享正在执行任务的容器。

#### Scenario: 执行资源空闲时消费任务

- **WHEN** 至少有一个执行资源处于空闲状态且任务队列中存在待处理任务
- **THEN** 一个且仅一个执行资源消费该任务并开始执行，其他执行资源不得重复执行同一任务

#### Scenario: 执行资源全部忙碌时排队

- **WHEN** 所有执行资源都在执行任务且任务队列尚未达到容量上限
- **THEN** 新任务进入队列等待，不创建超过当前调度规则允许数量的执行资源

### Requirement: 容器执行资源必须遵循核心与最大数量规则

系统 SHALL 在服务启动后保持配置数量的核心执行资源；当任务队列达到扩容条件时，系统 SHALL 在最大执行资源数量以内创建临时执行资源；临时资源空闲超过配置的存活时间后 SHALL 被回收。

#### Scenario: 服务启动创建核心资源

- **WHEN** 判题服务完成启动
- **THEN** 核心执行资源已创建并可消费任务，且不会因为空闲而被回收

#### Scenario: 核心资源初始化失败

- **WHEN** 判题服务启动期间无法创建或启动任一必需的核心容器
- **THEN** 判题服务启动失败并保持未就绪，不接受新的判题任务

#### Scenario: 队列积压触发临时扩容

- **WHEN** 核心执行资源均忙碌且任务队列已满，并且当前执行资源数量小于最大数量
- **THEN** 系统创建临时执行资源消费任务，执行资源总数不得超过最大数量

#### Scenario: 低峰期回收临时资源

- **WHEN** 临时执行资源没有正在执行的任务并且空闲时间超过配置的存活时间
- **THEN** 系统回收该临时资源，核心执行资源和正在执行的任务不受影响

### Requirement: 满载时必须执行可观察的拒绝策略

系统 SHALL 在任务队列已满、没有空闲执行资源且无法再创建容器时拒绝新任务，并向同步调用方返回 `SYSTEM_BUSY`（系统繁忙）结果；异步消息不得因本地拒绝而被静默丢弃。

#### Scenario: 同步任务达到容量上限

- **WHEN** 所有执行资源都忙碌、任务队列已满且已达到最大执行资源数量，无法再创建容器
- **THEN** 同步提交立即收到 `SYSTEM_BUSY`（系统繁忙）结果，任务不会进入执行队列

#### Scenario: 异步任务达到容量上限

- **WHEN** RabbitMQ 消息对应的任务无法提交到容器执行池
- **THEN** 消费者使用 `basicNack(requeue=false)` 将消息交给死信流程，死信消费者更新 Redis 为失败状态，系统不得静默丢失该任务

### Requirement: 判题完成和容器故障必须正确收敛

系统 SHALL 在判题任务完成后清理用户代码及编译产物；用户代码导致的判题失败不得破坏健康容器的后续复用；容器或 Docker 通信故障 SHALL 隔离失效容器并恢复核心资源数量。

#### Scenario: 用户代码判题失败后复用健康容器

- **WHEN** 用户代码编译失败、输出不匹配、超时或超出资源限制，且容器仍健康
- **THEN** 系统记录判题失败结果，清理任务文件，并允许该容器继续消费后续任务

#### Scenario: 容器执行异常后隔离恢复

- **WHEN** 容器退出、无法执行命令或 Docker API 调用失败
- **THEN** 系统不再将该容器分配给新任务，清理或销毁失效容器，并为核心资源补建可用容器

#### Scenario: 异步任务完成后确认消息

- **WHEN** 异步判题任务已经完成结果写入和必要的失败处理
- **THEN** RabbitMQ 消息才被确认；服务在确认前异常退出时，消息仍可被重新投递或进入既定死信流程
