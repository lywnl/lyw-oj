## Purpose

为判题提交入口提供按鉴权用户和系统总量共享的频率控制，使重复提交、集中提交及限流存储故障具有明确的拒绝行为，并让普通提交与消息提交在多应用实例间遵循一致的额度与生命周期规则。

## ADDED Requirements

### Requirement: 用户提交频率必须跨入口共享

系统 SHALL 按鉴权用户 ID 隔离提交额度，默认同一用户每 5 秒允许一次提交尝试。普通提交与消息提交、不同题目和同环境应用实例 SHALL 共享该用户额度。

#### Scenario: 用户冷却期内跨入口提交
- **WHEN** 用户刚通过用户额度检查，并在 5 秒内通过另一入口或提交另一道题
- **THEN** 新请求被用户频率规则拒绝

#### Scenario: 不同用户额度隔离
- **WHEN** 两个不同鉴权用户各有可用用户额度且总量额度充足
- **THEN** 两个用户都可以通过检查，不能因另一用户的冷却而被拒绝

#### Scenario: 同用户并发争抢
- **WHEN** 多个同用户请求在无可恢复额度的同一冷却期内并发检查
- **THEN** 最多一个请求通过用户额度检查

### Requirement: 提交总量必须跨用户和实例共享

系统 SHALL 为同环境两个提交入口提供共享总量额度，默认所有用户与应用实例合计每秒允许三次。该值是准入频率初值，SHALL NOT 被解释为已经验证的服务器安全吞吐量。

#### Scenario: 总量额度耗尽
- **WHEN** 无其他请求参与，四个有用户额度的请求在尚未恢复总量额度的一个周期内提交
- **THEN** 前三个通过总量检查，第四个收到总量超限拒绝

#### Scenario: 不同实例共享总量
- **WHEN** 两个应用实例使用同一环境的限流数据
- **THEN** 两实例合计仍受同一总量上限限制

#### Scenario: 周期结束后恢复
- **WHEN** 已使用的总量额度经过配置周期
- **THEN** 新的合格提交可以重新取得已恢复的额度

### Requirement: 限流必须位于受理副作用之前

系统 SHALL 在现有基础参数校验与身份校验通过后执行频率检查，并在通过之前不查询题目、不生成提交 ID、不写等待状态、不发送判题消息或调用判题服务。

#### Scenario: 无效请求不消耗额度
- **WHEN** 请求未通过现有基础参数或身份校验
- **THEN** 返回现有错误行为，不调用限流存储

#### Scenario: 拒绝请求不进入判题链路
- **WHEN** 用户超限、总量超限或限流存储检查失败
- **THEN** 请求在题目查询和受理副作用之前结束

#### Scenario: 放行后沿用原有提交行为
- **WHEN** 两层检查均通过
- **THEN** 普通提交与消息提交继续各自现有的受理、判题或发送流程

### Requirement: 提交尝试必须先扣用户再扣总量

系统 SHALL 先检查并消耗用户额度，再检查总量。用户超限时 SHALL NOT 消耗总量额度；已消耗的额度 SHALL NOT 因后续总量拒绝、业务失败、发送失败或判题失败而退还。

#### Scenario: 用户超限不占用总量
- **WHEN** 用户额度已耗尽
- **THEN** 立即拒绝，其他用户仍可使用尚存总量额度

#### Scenario: 总量拒绝保留用户冷却
- **WHEN** 用户额度取得成功但总量检查失败
- **THEN** 请求被拒绝，该用户冷却继续有效

#### Scenario: 后续失败不退还额度
- **WHEN** 两层检查通过后发生消息发送失败或后续业务失败
- **THEN** 保留已经消耗的额度，并沿用该业务失败原有响应

### Requirement: 超限和存储故障必须返回明确错误

系统 SHALL 对用户超限返回 HTTP 429 / code 3602 / “提交过于频繁，请稍后再试”，对总量超限返回 HTTP 429 / code 3603 / “当前提交请求较多，请稍后再试”，对限流存储连接或命令超时故障返回 HTTP 503 / code 3604 / “提交服务暂时不可用，请稍后再试”。拒绝响应 SHALL 使用现有 code、msg、data 结构，data 为 null。

#### Scenario: 超限 HTTP 响应正确
- **WHEN** 任一提交入口触发用户或总量超限
- **THEN** HTTP 状态、业务码和提示均对应原因，并且不返回提交 ID

#### Scenario: Redis 故障时拒绝本次提交
- **WHEN** 限流检查遇到连接失败或命令响应超时
- **THEN** 在有限等待后返回 503，不能按放行处理

#### Scenario: 现有非限流错误保持原响应
- **WHEN** 发生本轮新增错误码之外的已有业务异常
- **THEN** 原有 HTTP 和业务错误处理行为保持兼容

### Requirement: 限流状态必须有明确生命周期

系统 SHALL 在首次使用时初始化规则，已有规则不因普通请求、重启或客户端重建而重置额度。用户状态默认空闲 10 分钟后过期，并随检查活动续期；总量状态持续保留。不同环境 SHALL 使用不同名称空间。

#### Scenario: 初始化已有规则不恢复额度
- **WHEN** 限流对象已存在且额度已耗尽，客户端再次初始化或重建
- **THEN** 仍被拒绝直至相应额度正常恢复

#### Scenario: 用户空闲状态过期后重建
- **WHEN** 用户限流状态超过配置空闲时间没有活动
- **THEN** 该状态及其关联数据过期，后续提交能够重新初始化

#### Scenario: 活动延长空闲期限
- **WHEN** 用户在空闲过期前继续接受频率检查
- **THEN** 用户状态空闲期限从最近检查活动重新计算

#### Scenario: 环境隔离
- **WHEN** 两个环境使用不同限流名称空间
- **THEN** 一个环境的额度使用不影响另一环境

### Requirement: 限流接入必须复用现有单机连接并约束等待

系统 SHALL 使用现有单机 Redis 的生效地址、数据库、认证和 SSL 配置，保留现有缓存访问能力。新增客户端 SHALL 采用惰性连接，连接与命令超时默认各 1 秒、命令重试 0 次、连接池上限 8、最小空闲 1，并在应用关闭时释放。配置额度和周期 SHALL 为正，用户空闲期限 SHALL 不小于用户限流周期。

#### Scenario: 客户端兼容现有缓存
- **WHEN** 限流客户端与已有缓存客户端连接同一个隔离 Redis
- **THEN** 限流检查及原有状态缓存读写都成功

#### Scenario: 启动时不额外强制连接 Redis
- **WHEN** 创建新增客户端配置但尚未执行提交检查
- **THEN** 新增客户端不因 Redis 暂不可用而在配置阶段建立强制连接

#### Scenario: 无效配置及时失败
- **WHEN** 配置含非正额度或周期、过短空闲期限或不支持的连接拓扑
- **THEN** 明确报告配置错误，不能静默连接其他 Redis 或使用不受限的规则

### Requirement: 参数调整与诊断必须遵循受控边界

系统 SHALL 支持停服后统一调整配置和重新初始化本功能限流状态，普通重启保留状态。维护操作 SHALL 只处理对应环境下本功能逻辑限流器的关联数据。诊断 SHALL 区分超限与存储故障，普通超限不输出异常堆栈，不记录用户源码和连接凭据。

#### Scenario: 停服后统一调整规则
- **WHEN** 所有提交入口停止，操作者按限定名称空间清理本功能逻辑限流器并以一致新配置启动
- **THEN** 新规则生效，其他 Redis 业务数据不受影响

#### Scenario: 拒绝日志不暴露提交内容
- **WHEN** 用户超限、总量超限或存储检查失败
- **THEN** 仅记录必要的原因类别，不记录源码或认证凭据
