## MODIFIED Requirements

### Requirement: 满载时必须执行可观察的拒绝策略

系统 SHALL 在任务队列已满、没有空闲执行资源且无法再创建容器时拒绝新任务，并向同步调用方返回 `SYSTEM_BUSY`（系统繁忙）结果；异步消息不得因本地拒绝而被静默丢弃。

#### Scenario: 同步任务达到容量上限
- **WHEN** 所有执行资源都忙碌、任务队列已满且已达到最大执行资源数量，无法再创建容器
- **THEN** 同步提交立即收到系统繁忙提示，任务不会进入执行队列，也不写真实提交记录

#### Scenario: 异步任务达到容量上限
- **WHEN** RabbitMQ 消息对应的任务无法提交到容器执行池
- **THEN** 消费者使用 `basicNack(requeue=false)` 交给死信流程，死信按原 submitId 条件更新统一缓存的系统错误，不覆盖已有真实结果且不插入提交表

#### Scenario: 死信状态无法写入
- **WHEN** 死信状态写入共三次均失败，间隔依次为 1 秒和 2 秒
- **THEN** 系统在线程外停止独立的单消费者、预取数为 1 的死信监听器，未确认消息重新留在死信队列，普通监听不受暂停影响，人工恢复服务后继续处理

### Requirement: 判题完成和容器故障必须正确收敛

系统 SHALL 在判题任务完成后清理用户代码及编译产物；用户代码导致的判题失败不得破坏健康容器的后续复用；容器或 Docker 通信故障 SHALL 隔离失效容器并恢复核心资源数量。

#### Scenario: 用户代码判题失败后复用健康容器
- **WHEN** 用户代码编译失败、输出不匹配、超时或超出资源限制，且容器仍健康
- **THEN** 系统记录真实判题失败结果，清理任务文件，并允许该容器继续消费后续任务

#### Scenario: 容器执行异常后隔离恢复
- **WHEN** 容器退出、无法执行命令或 Docker API 调用失败
- **THEN** 系统不将故障伪装为真实判题记录，不再将失效容器分配给新任务，清理或销毁失效容器，并为核心资源补建可用容器

#### Scenario: 异步任务完成后确认消息
- **WHEN** 异步判题真实结果已提交数据库，或主键冲突后复用了已提交结果
- **THEN** 尝试更新真实缓存后确认消息，缓存失败不重新判题；ACK/NACK 异常与业务重试隔离，关闭故障通道让未确认消息由 Broker 重投
